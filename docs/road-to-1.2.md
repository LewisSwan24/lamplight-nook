## 1. 目标

用户可以把一件大事交给小店做上几个星期，比如一个网站、一本小册子或一套表格：

- **记得住：** 一件大事是一个项目，有自己的文件夹、时间线和每一版。店员每轮开工前都知道项目是干什么的、做到了哪里。
- **说得清：** 开工前可以先和阿灯聊几句，聊完生成一张委托单，聊天花的钱单独记。
- **不用守着：** 两单可以同时做，关到托盘也照样做，做完发通知。可以排定时委托。睡眠、断网、关机以后能接着做，不重复花钱。
- **管得住钱：** 每轮、每个项目、每个月各有上限，快到时提前说。
- **看得懂：** 两组人同时干活时，谁在为哪个项目忙，一眼看得出来。

## 2. 流程

照 `docs/road-to-1.1.md` 第 2 节，有四处不同：

1. 集成分支是 `release-1.2`，从 `release-1.1` 开，不从 `main` 开。工作包分支从它开，名字用编号，比如 `b1-projects`。
2. CHANGELOG 写在 “Unreleased (1.2)” 下面。
3. 1.1 发布时，`release-1.1` 照旧压成一个提交合进 `main`。之后用 `git rebase --onto main release-1.1 release-1.2` 把 1.2 的提交搬到 `main` 上。冲突太多就改成把 `main` 合进 `release-1.2`。1.1 在发布关卡里改的东西，也要合进 `release-1.2`。
4. 真实运行用安装好的应用里存的那把 Key，和 1.1 的 A7 一样，不另要测试 Key。每个工作包开跑前单独报预算，Lewis 说了才跑。

## 4. 工作包

### B1 项目模型和数据迁移

**现状：**

- 笔记本 `memory.json` 里一单一条 `CommissionMemo`（`app/shared/types.ts:388-418`），记着文件夹、委托单、最后一轮的会话号和每轮的统计。
- “再改改”不开新条目，记在同一条的 `asks` 和 `rounds` 里（`app/main/memory.ts:91-116`）。`asks` 只留最近 10 轮，`rounds` 留 50 轮（`memory.ts:13`、`:15`）。几个星期的项目很容易超过 10 轮。
- 每单按“日期-时刻-标题”新开一个文件夹（`app/main/agent-runner.ts:266-268`，`app/main/index.ts:462`）。A6 借来的文件夹直接当工作目录（`index.ts:474-480`）。
- 再改一轮之前，`versions/<委托号>/` 存一份“上一版”，每次覆盖，只有一份，上限 50MB（`app/main/versions.ts:7`、`:83-93`）。借来的文件夹另记原样和新做的文件（`versions.ts:53-56`、`:126` 起）。
- 账本 `spend.json` 按“文件夹|会话号”记账（`app/main/spend.ts:7`、`:27-42`），一单花了多少就是同一个文件夹所有会话的和（`spend.ts:74-76`）。
- 数据版本是 3（`app/main/migrate.ts:16`），升级步骤写在 `STEPS` 里（`migrate.ts:39`），升级前先备份。
- 笔记本只读认识的字段（`memory.ts:284-299`），保存时整个写回（`memory.ts:301-305`）。所以 1.2 的数据被 1.1 打开存一次，新加的字段就没了。

**设计：**

- 项目是一个文件夹加上它的全部委托、每一轮和每一版。笔记本加一张表：

```ts
type Project = {
  id: string;              // p<时间>，和委托号一样防重
  title: string;           // 默认取第一单的标题，用户能改
  folder: string;
  lent?: boolean;          // A6 借来的文件夹
  created: string;         // YYYY-MM-DD
  commissions: string[];   // 委托号，旧的在前
  rounds: ProjectRound[];  // 时间线，旧的在前，不设条数上限
  brief?: ProjectBrief;    // B3
  capUsd?: number;         // B8
  from?: { project: string; round: number };  // B2 岔出去的
  archived?: boolean;
};
type ProjectRound = {
  n: number; commission: string; date: string;
  ask?: string;            // 第一轮没有，是委托单本身
  summary?: string; usd?: number; seconds?: number; failure?: string;
  version?: string;        // B2 的版本号
  restoredFrom?: number;   // 这一轮是“退回到第几轮”
};
```

- `CommissionMemo` 加 `project` 字段。`Memory` 加 `projects`，`read()` 认这个字段。
- 项目里接着做有两种。一种是现在的“再改改”，同一条委托多一轮。另一种是在同一个文件夹里开一张新委托单，比如“再加一页博客”，新开一条委托，归同一个项目。两种都往项目的时间线上加一轮。
- 新委托照旧新开文件夹，也就是一个新项目。从项目板上点“在这个项目里再做一单”，才用项目的文件夹。
- 迁移是第 4 步，数据版本从 3 升到 4：
  - 每条委托变成一个只有一单的项目，标题和文件夹照抄。项目号由委托号推出来（`c123` 变成 `p123`），迁两次结果一样。
  - 时间线由第一轮加上 `asks` 拼出来。1.1 以后的作品有 `rounds`，用时和失败原因照抄。每轮花了多少以前没记，旧的轮次不写 `usd`，项目合计照旧从账本算。
  - 没做完的委托也迁，项目状态是“停下了”。借来的文件夹记 `lent`。
  - `versions/<委托号>/` 原地不动，B2 再把它挂到倒数第二轮上。
  - 照 `migrate.ts` 的做法，先备份，失败停在 3。
- 开店时还要补一遍：没有项目的委托，补一个只有一单的项目。这条管的是先用 1.2、又装回 1.1 存过一次、再升回 1.2 的情况。数据版本标记还是 4，迁移不会再跑，靠这一步补回来。
- 作品架照旧按委托列，点开能跳到所属的项目。迁移以后一件作品就是一个项目，老用户看到的东西一样不少。
- `VersionStore` 的编号检查只认 `c` 开头（`versions.ts:67-71`），要加上 `p` 开头的项目号。

**完成标准：** 新的 `tests/projects.test.ts` 覆盖建项目、两种接着做、补项目和防重。`tests/migrate.test.ts` 加第 4 步：普通作品、改过三轮的、没做完的、借来文件夹的，各迁一遍，再迁一次结果不变。`tests/memory.test.ts` 加 `projects` 字段的读写。新场景 `projects`：一家 1.1 的店有五件作品，含一件失败、一件借来的文件夹。开店后五个项目都在，作品架一样，再开一次不重复迁。`upgrade` 场景照旧过。`node tools/sim/accept.mjs --only projects,upgrade,baddata,moved,inplace`。

**做法：**

- 类型在 `app/shared/types.ts`：`Project`、`ProjectRound`，还有 B3 的 `ProjectBrief`。B4 的 `consults` 已经在 `Project` 上占好位置，B2、B3、B8 要的字段也都在，后面的包只管写，不用再迁。
- 新模块 `app/main/projects.ts`。`addProjects()` 给没有项目的委托补项目。迁移第 4 步和开店时都调用这个函数，两处结果一模一样。
- 笔记本读项目时整条保留，不挑字段。以后的版本在项目上加了字段，1.2 打开再存，这些字段也还在。
- 1.1 存笔记本会丢掉 `projects`，委托上的 `project` 字段却留着。所以开店补项目时，`project` 相同的委托合回同一个项目，其余的才一单一个。
- `remember()` 建项目，或者照 `project` 归进已有的项目。`revise()` 往时间线上加一轮。停下后接着做、同一轮改动再试一次，都算同一轮：用时和花费相加，结局以最后一次为准。
- 每轮的 `usd` 是这一轮让账本多出来的钱，取自 `spend.record()` 的返回值。
- 第 4 步把 `memory.json` 和 `memory.last-good.json` 一起迁，这是 `migrate.ts` 开头那条注释的要求。
- 作品架的每一件多了 `project` 字段，留给 B2 跳到项目用。
- `VersionStore` 认 `c` 和 `p` 两种开头的编号。

**暂定（2026-11-15）：**

- 项目“做好了”还是“停下了”不单独存，看项目里最后一单委托的结果（`projectSettled()`）。在做、排队、等你回答这三种由主进程给，留给 B2、B5。
- 旧作品的轮次和用时从后往前对：1.0 改过、1.1 又改过的作品，只有最后几轮有用时。重试多出来的统计不进时间线，委托自己的 `rounds` 原样留着，账簿页照旧。
- 旧作品第一轮的日期，取第一次改动的日期，没改过就取委托的日期。
- 迁移前的委托 `asks` 只留了 10 条，改过十次以上的作品，时间线只能从留下的那 10 条拼。
- 借来的文件夹里再开一张新委托单，照旧算一个新项目。B5 排队时，重叠的借来文件夹再按同一个项目处理。
- 用户移动了文件夹、在新位置找回作品时，项目的文件夹也跟着改。同一个项目里的其他委托不跟着改，等 B2 有多单的项目再说。
- “在这个项目里再做一单”目前只有笔记本这一层（`remember()` 带 `project`），入口和主进程那一段跟着 B2 的项目板做。

### B8 项目和每月的预算

**现状：**

- 只有每轮上限：设置里的 `budgetUsd`，默认 $3（`app/main/settings.ts:15`），可选 1、3、5、10 和不限（`app/shared/types.ts:72`）。它直接交给 SDK 的 `maxBudgetUsd`（`app/main/index.ts:365`，`app/main/agent-runner.ts:229`）。
- 到了上限，预算卡给出“接着做”和“看看已经做好的”（`app/renderer/ui/run.ts:108`）。
- 账本能算本月和每个月的合计（`app/main/spend.ts:78-90`），按本地时间分月（`app/shared/localday.ts`），笔记本的账簿页在用。
- 一轮花了多少，要等这一轮结束才知道（`index.ts:377`）。SDK 的说明写着 `maxBudgetUsd` 只算这次 `query()` 开始以后的花费，续上的会话会带着之前的合计（`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:6031-6033`）。1.1 真跑时，旅行攻略超过每轮 $1 的上限 5 美分才停（`docs/road-to-1.1.md` 第 7 节）。

**设计：**

- 设置加每月上限 `monthCapUsd`，默认值见 Q-B4，可选 10、20、50、100 和不限。项目卡上加项目上限 `capUsd`，可选不限、5、10、20、50，默认不限。
- 新模块 `app/main/budget.ts` 管“预留”。一轮开工时，先算还剩多少：
  - 本月剩余 = 每月上限 − 本月已花 − 别的单正在预留的。
  - 项目剩余 = 项目上限 − 项目已花 − 同项目别的单正在预留的。
  - 这一轮的上限取每轮上限、本月剩余、项目剩余三者中最小的，作为 `maxBudgetUsd` 交给 SDK，同时记为预留。
  - 一轮结束，按账本记下的实际花费结算，没用完的退回。
- 剩余不到 $0.50 就不开工，弹卡说清是哪一个上限到了，按钮去设置或项目卡。$0.50 是为了留出超支的余地，B5 真跑时再量。
- 提前提醒：一轮结算后，本月或项目第一次过了八成，阿灯说一句，委托单的预算提示也写上还剩多少。每个月、每个项目各只说一次，记在笔记本里。
- 到了上限：正在做的单只能用完自己的预留，新的单不开工，定时委托跳过，在项目板上记一笔，再发通知（B6）。
- 老用户升级：前三个月里有一个月超过默认值，默认值就往上提一档，阿灯说一次。
- 商量（B4）的花费也算进本月和项目。
- 账本记的是 Claude Code 的估计，设置里的说明照旧写明以 Console 为准。被叫停的一轮可能漏记，见 B7。

**完成标准：** 新的 `tests/budget.test.ts` 覆盖预留和结算、两单同时预留、跨月（本地午夜）、项目上限、八成只提醒一次和老用户提档。`tests/settings.test.ts` 加 `monthCapUsd`。新场景 `monthcap`：把 `SIM_COST` 调高，第三单过八成时阿灯说了一次，第四单开工前被拦，换到下个月又能开工。月份靠一个只在没打包时生效的时钟变量来换，B6 也要用。新场景 `projectcap`：项目上限到了，同项目的新单被拦，别的项目照常。`budget`、`ledger`、`stats` 场景照旧过。提醒卡和拦下卡中英文截图都看过。

**做法：**

- 新模块 `app/main/budget.ts`。`Reservations` 按运行号记下每一轮占着的钱。开工时 `reserve()` 取每轮上限、本月剩余、项目剩余三者中最小的，交给 SDK 的 `maxBudgetUsd`，同时记成预留。
- 别的单算剩余时，正在占着的钱也一并减掉。一轮结束、账本记完以后，`settle()` 把预留放掉，实际花了多少以账本为准。B5 两单同时跑，直接用这一套。
- 剩余不到 $0.50（`MIN_START_USD`）就不开工。新委托在建文件夹之前问，再改改在存“上一版”之前问，被拦下时什么都不留。
- “接着做”和崩溃后的接着做，在 `runJob()` 开头问。拦下以后它还是“再试一次”的那一单，上限调高了点“接着做”就能续上。
- 这一轮的上限如果是本月或项目的剩余定的，SDK 因为预算停下时，卡片说的是那个上限，不说每轮上限。
- 拦下卡用讲钱的那种朴素卡片。每月上限的卡有“去设置”，直接打开设置的开工页。项目上限的卡有“打开笔记本”。
- 一轮结算后 `warnings()` 看本月和项目是不是第一次过了八成。过了的话，成品卡上多一句阿灯的提醒，停下的卡上也会有。说过的月份和项目号记在笔记本的 `budgetSaid` 里。
- 本月过了八成以后，委托单的预算提示多一句这个月还剩多少。
- 设置加 `monthCapUsd`。设置文件里没有这一项时，由 `startingMonthCap()` 定，定完马上写回文件，以后不再重算。提了档的老用户，开店时阿灯用一张卡说一次。
- 项目上限写在 B1 留好的 `capUsd` 上。项目花了多少，按项目用过的文件夹从账本加起来。
- 时钟在 `app/main/clock.ts`。没打包时读 `LAMPLIGHT_CLOCK`，钱和月份都按它算。验收工具的 `launch()` 加了 `clock`。
- 替身 Claude 做完一轮后，把花费带进 `--resume`，和真的 Claude Code 一样。这样再改改的花费才记得上账。

**暂定（2026-11-15）：**

- 八成的提醒写在成品卡上，不另弹卡，也不用气泡。提醒挨着这一轮花了多少，不会错过。
- “前三个月”算本月加前三个整月。只提一档，花得再多也只到 $50。
- 项目上限先放在笔记本里，挂在每个项目最近那一单下面。B2 做项目板时搬过去。
- 本月或项目上限叫停的一轮，卡上照样有“接着做”，钱还不够就再拦一次。新单和再改改在开工前就被拦，卡上没有“接着做”。
- 借来的文件夹里有两个项目时，账本按文件夹记，两个项目的花费算在一起。
- $0.50 的余地照设计先用，B5 真跑时再量。
- 商量（B4）的花费记进同一本账，本月和项目都算上，做法见 B4。定时委托跳过、记一笔、发通知，留给 B6。

### B4 先商量再动手

### B3 项目记忆

**现状：**

- 现在每单的提示词后面都带一段笔记：最近 20 单用户回答过的问题，以及同名委托以前卡过的地方（`app/main/memory.ts:275-282`、`:10`，`app/main/commission.ts:101`）。注释写着每条笔记每单都要付钱。
- 再改改时，Claude Code 还留着上次的会话就接着用（`app/main/index.ts:346`），没有就从文件夹重新开始（`commission.ts:159`）。接着用会话，上下文一轮比一轮长。
- `settingSources: []`（`app/main/agent-runner.ts:222`），Claude Code 不读文件夹里的 `CLAUDE.md`，项目背景只能写进提示词。
- 结果消息里有 `usage`（`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:6037`），应用只取了 `total_cost_usd`（`agent-runner.ts:245`）。

**设计：**

- 项目的 `brief` 有四样：

```ts
type ProjectBrief = {
  purpose: string;      // 项目是干什么的：第一张委托单的要求和说明，用户能改
  prefs: string[];      // 用户定过的偏好：项目里回答过的问题，加上用户手写的，最多 12 条，每条最多 120 字
  lastRound?: string;   // 上一轮做到哪里：上一轮店员的总结，自动更新
  edited?: string;      // 用户最后改动的日子
};
```

- 每轮开工时，应用把 `brief` 和最近 3 轮要改的地方拼成一段“项目背景”，放在提示词前面。不另外调用模型去总结，不多花钱。
- 每轮的上限：项目背景最多 2,000 个字符，暂定，真跑以后再调。超了先删最旧的“要改的地方”，再删多出 8 条的偏好，最后才截短“是干什么的”。
- 项目里的轮次不再带全店最近 20 单的问答，只带这个项目的偏好，免得重复付钱。
- 接着用会话还是重开：每轮记下结果里的输入 token 数（`RoundStat.contextTokens`）。上一轮超过 150k，或者会话上次用是 7 天以前，就重开一个会话，靠项目背景和文件夹清单接上。两个数都是暂定，真跑以后再定。
- 用户能看能改：时间线最上面一块“店员记得的”，四样都列出来，可以改、删、加。还有一个“忘掉这个项目”，清空 `brief`。“忘掉一切”照旧连项目记忆一起清。
- 真 Key 约 $4：同一个小网站项目跑两遍，每遍五轮。一遍带项目背景并按规则重开，一遍照现在一直接着用会话。比较每轮花费，结果记进第 7 节，再定上面两个暂定的数。

**完成标准：** 新的 `tests/project-brief.test.ts` 覆盖拼法、2,000 字的裁剪顺序、问答并进偏好、用户改过的不被下一轮冲掉、重开会话的两条规则。`tests/templates-prompts.test.ts` 的快照加项目背景的情况。新场景 `projectmemo`：项目做两轮，替身的日志里第二轮的提示词有用途、偏好和上一轮的总结，长度不超过上限。用户改了偏好，第三轮的提示词里是改过的。中英文“店员记得的”截图都看过。

**做法：**

- 新模块 `app/main/project-brief.ts`：`briefOf()` 读出项目的 `brief`，`afterRound()` 在一轮结束后更新，`editedBrief()` 收下用户改的，`projectBackground()` 拼项目背景，`newSession()` 判断要不要重开会话。
- 用户没改过、也没忘掉过的项目，笔记本里不存 `brief`。要用时从笔记本现有的东西读出来：第一单的要求和说明，项目里回答过的问题，最后一轮的总结。迁移来的老项目和岔出去的项目都这样，不用补数据。用户改过或忘掉以后，`brief` 才写进笔记本，以后每轮只往里并新的问答，换掉“上一轮做到哪里”。
- 项目背景只给“再改改”的轮次，放在提示词最前面，接着用会话和重开会话都带。这些轮次的笔记不再带全店的问答，同名委托卡过的地方照旧带。
- 一轮的 `contextTokens` 是结果里 `usage` 的输入、写缓存和读缓存三项相加，记在委托的 `rounds` 上。再改改开工前看最后一轮：超过 150k，或者那一轮的日子离今天超过 7 天，就不接着用会话。
- 时间线最上面一块“店员记得的”，和时间线一起滚动。“改一改”把四样换成输入框，偏好可以删、可以加。“忘掉这个项目”和退回一样要点两次。
- 新场景 `projectmemo`。替身的 `page` 一出在这个场景里先问一次主色，回答就是项目的第一条偏好。

**暂定（2026-11-15）：**

- 偏好写成“问题 回答”。问题末尾没有问号或冒号时，中间加一个冒号。同一个问题再答一次，换掉旧的那条。
- 偏好满 12 条后再并进新的问答，删最旧的一条，用户手写的也一样。用户自己改时只留前 12 条。
- “上一轮做到哪里”最多 500 字。这样偏好删到 8 条以后一定放得下，只截“是干什么的”就够了。“是干什么的”用户最多能写 4,000 字。
- 偏好超出时留最新的 8 条。
- “上一轮做到哪里”每轮都换成新的总结，用户改过也一样，它本来就是上一轮的事。用户改过的“是干什么的”和偏好，下一轮不动。
- “忘掉这个项目”留下一个空的 `brief`，不是删掉。删掉的话，下一轮又会从笔记本读回原样。`forgotAt` 记下忘掉时有几轮，这以前要改的地方不再进提示词。这个项目各单的会话号也删掉，因为接着用会话，店员照样记得。
- 接着做停下的一单（`continuePrompt`）：接着用会话时只说“接着做”，不带项目背景。不接着用时，再改改的轮次带背景，新委托的第一轮不带，它本身就是那张委托单。
- 重开会话时，提示词里照旧只写“文件都在这个文件夹里，先看看”，没有附文件清单，店员自己会看。
- `usage` 只算主循环，不算帮手。150k 和 7 天、2,000 字的上限，都等真 Key 那一遍（约 $4）跑完再定，那一遍还没跑。

### B5 多单并行

**现状：** 主进程和渲染进程到处默认只有一单在跑。

- 主进程只有一个 `current`（`app/main/index.ts:61`）。开新单和再改改都拒绝，返回 `busy`（`index.ts:326`、`:457`、`:487`）。
- 记用户回答的 `broker.onAnswered` 每单开工时重新赋值（`index.ts:339`），两单同时跑会记串。“再试一次”的 `lastFailed` 和崩溃后留下的 `leftover` 都只有一个（`index.ts:81-82`）。`pending.json` 只存一单（`app/main/pending.ts:22-43`）。
- 发给渲染进程的事件不带委托号（`app/shared/types.ts:346-364`，`index.ts:155-163`），要用户回答的请求也不带（`app/main/decision-broker.ts:17-23`）。小窗口和托盘的进度也只有一份（`index.ts:159-161`）。
- 渲染进程只记一个 `running`（`app/renderer/main.ts:452`），事件都交给同一个翻译器（`main.ts:699`）。
- 跑腿排队按帮手算：小橘忙时第二件给小豆，再多就排队（`app/renderer/translator/translator.ts:130-147`）。
- 每轮上限靠 SDK 的 `maxBudgetUsd`（`index.ts:365`），花费要到一轮结束才知道（`app/main/agent-runner.ts:241-248`）。所以“并行的单共用一个总上限”只能靠 B8 的预留，没法边跑边看。
- 文件只靠单实例锁防止两家店同时写（`index.ts:770-771`）。一家店里两单同时写笔记本和账本，现在的写法每次都整个重写文件，不会写坏。不过两单要先读后写同一份数据时，得在一个地方排好先后。

**设计：**

- 每一轮有一个运行号 `r<时间>`。`current` 换成 `runs: Map<运行号, Run>`。每个 `Run` 有自己的中止开关、计时、卡住记录和回答记录，`broker.onAnswered` 换成按运行号分发。
- 事件、要回答的请求、结果、小窗口和托盘的消息都带上运行号和项目号。
- 同时最多两单，见 Q-B2。多的进队列，项目板上显示“排队”。规则：
  1. 同一个项目同一时间只跑一单，因为是同一个文件夹。借来的文件夹有重叠也算同一个。
  2. 先来先做。用户自己点的排在定时委托前面。
  3. 排队的单可以取消，不花钱。
  4. 因为预算或断网停下的单不占位置。等用户回答的单占着位置，项目板上写明在等谁。
  5. B8 的剩余不够，单子留在队里，写明在等钱，不自己开工。
- 要回答的卡片一次只弹一张，标题前写项目名，多的排着。
- 两单的花费分别结算，各记各的会话。结果卡写明是哪个项目的。
- Claude Code 每单一个进程，两单就是两个。真跑时量一下内存，写进第 7 节。
- 真 Key 约 $5：两个小委托同时跑两次，再排一单进队，账本合计和 Console 对一下。

**完成标准：** 新的 `tests/runs.test.ts` 覆盖队列的五条规则。`tests/decision.test.ts` 加运行号，两单的回答不串。`tests/translator.test.ts` 加两单的事件交错。`tests/budget.test.ts` 加两单同时预留。新场景 `parallel`：替身同时跑两单，都做完，结果各归各的项目，账本两条都在，第三单排队后自己开工。新场景 `parallelcap`：本月只够一单，第二单在队里等钱。`budget`、`neterror`、`crash`、`stopclose`、`stopdone`、`revise`、`inplace`、`apprentice`、`mini`、`meeting` 照旧过。

### B6 后台跑和定时委托

**现状：**

- 已经能关到托盘：设置里的 `closeToTray`，默认关（`app/main/settings.ts:32`）。打开以后，关窗口只是藏起来，委托照常做（`app/main/index.ts:117-123`）。藏起来时桌角有个小窗口（`index.ts:69-73`）。
- 有要用户回答的事时，托盘的灯闪，每件事发一条系统通知，`notify` 默认开（`app/main/tray.ts:57-76`）。做完、失败和预算停下都不发通知。
- 托盘菜单只有“显示”和“退出”（`tray.ts:34-38`）。
- 没有定时委托，也没有开机自启，代码里找不到 `setLoginItemSettings`。
- 要回答的请求不会超时（`app/main/decision-broker.ts:3-7`），没人在时就一直等。

**设计：**

- 关到托盘照旧默认关，见 Q-B3。有委托在做时关窗口，现在的问题卡有“继续做”和“停下并关闭”两个按钮（`index.ts:124-138`）。有托盘时多一个“收进托盘接着做”，点了只这一次收进托盘，不改设置。
- 通知：做完、失败、预算停下、要回答，四种都发。只在窗口不在眼前、`notify` 开着时发。通知里写项目名和结果，不写文件内容。点通知打开那个项目的结果卡。
- 托盘菜单列出在做和排队的单，各带状态。再加一项“暂停定时委托”。
- 定时委托存在数据文件夹的 `schedules.json`：

```ts
type Schedule = {
  id: string;                 // s<时间>
  project?: string;           // 在这个项目里接着做，没有就每次开新项目
  form: CommissionForm;       // 每次交的单子
  every: { kind: 'weekly'; weekday: number; time: string }   // time 是 HH:MM，本地时间
       | { kind: 'daily'; time: string }
       | { kind: 'once'; at: string };
  next: string;               // 下次的时刻
  last?: { at: string; result: 'done' | 'failed' | 'skipped'; why?: string };
  enabled: boolean;
};
```

- 从项目板的卡片上点“定期做”来排，比如每周一早上 9 点整理一份周报。
- 主进程里一个计时器，最多一小时醒一次，醒来对一遍时间，到点就把单子放进 B5 的队列。从睡眠醒来时也对一遍。

- 开机自启：设置里加“开机时在托盘里打开小灯屋”，默认关。用 `app.setLoginItemSettings`，带 `--tray` 参数，带这个参数时窗口一开始就藏着。

- 有定时委托但小店关着、也没开自启时，项目板上写一句“小店关着时，定时委托不会做”。

**完成标准：** 新的 `tests/schedule.test.ts` 覆盖每周、每天、一次三种的下次时刻，跨月和本地午夜，错过的规则（12 小时内补一次、更早跳过、多次只补一次）。`tests/settings.test.ts` 加自启开关。新场景 `background`：做到一半收进托盘，做完了，通知记了一条，点通知回到结果卡。新场景 `scheduled`：用 B8 的时钟变量拨到点，单子自己进队、做完。新场景 `missed`：关店越过一个时刻再开，补跑一次，越过两个只补一次。自启开关用替身检查传给 Electron 的参数。中英文的定期做面板和托盘菜单截图都看过，系统通知截不到，查日志。真 Key 约 $3：一个每周的周报跑两次，一单收进托盘跑完。

### B7 中断和跨天恢复

**现状：**

- 现在能接着做一单。开工时写 `pending.json`，拿到会话号就补上（`app/main/index.ts:330`、`:358`）。下次开店问一次（`index.ts:645-650`），用 `continuePrompt` 接着原来的会话（`app/main/commission.ts:186`）。
- 一轮结束就删掉 `pending.json`。只有用户在关店时选了“停下并关闭”才留着（`index.ts:405`、`:137`）。
- 断网、服务忙这些失败，只记在内存里的 `lastFailed` 上（`index.ts:81`、`:642`），关店就没了。
- 代码里没有 `powerMonitor`，也不管 Windows 的关机事件。
- 关机时会怎样没量过。窗口的关闭事件会弹同步的问题卡（`index.ts:124-129`）。要是没弹出来就走到 `will-quit` 中止了委托，`quitting` 还是假，`pending.json` 就被删了，下次开店接不上。这要在真机上看。
- 被叫停的一轮报不出花费（`index.ts:376` 的注释），账本里没有这一段。SDK 的说明写着，续上的会话从记录里保存的合计接着算，前提是记录里存了合计（`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts:6031-6033`）。中途被叫停的那一段能不能在续上时补回来，要真跑一次才知道。
- `crash`、`stopclose`、`stopdone`、`neterror` 场景只覆盖一单的情况。

**设计：**

- `pending.json` 换成 `pending/<运行号>.json`，一单一个文件。状态有在做、排队、用户停下、失败（断网、服务忙、预算）、被打断五种。旧的 `pending.json` 开店时转过来。`lastFailed` 也写进去，关店再开还能“再试一次”。
- 睡眠：
  - 有单在做时开 `powerSaveBlocker.start('prevent-app-suspension')`。这只挡空闲睡眠，合上盖子照样睡，做完就关。
  - `powerMonitor` 的 `suspend` 记下时刻。`resume` 以后，等网络通了，睡眠前后断网失败的单自动接着做一次。再失败就照旧弹失败卡。
- 关机：Windows 上接 `session-end` 和 `query-session-end`，不弹问题卡，把在做的单都记成“被打断”，中止，留着记录。下次开店弹一张卡，列出被打断的单，按钮是“都接着做”“一个个看”“都不要了”。
- 不重复花钱：
  1. 接着做一律续原来的会话，不从头再来。会话没了才从文件夹重新开始，和现在一样。
  2. 同一个运行号同一时间只能续一次，自动续和用户点的撞上了，后来的那个什么都不做。
  3. 定时委托被打断了就续上，不算错过，下次到点也不重跑。
  4. 账本照旧按会话的累计数记，续上以后合计变大才记差额（`app/main/spend.ts:27-42`）。被叫停那一段补不回来的话，就从录制里每条消息的 token 数估一个数，标成“估计”。每百万 token 的价格到时再查。
- 真 Key 约 $4：一单做到一半让电脑睡眠，一单做到一半关机，两单都接着做完。账本和 Console 对一下，看被叫停那段补没补上。

**完成标准：** 新的 `tests/pending.test.ts` 覆盖多单、旧文件转换、五种状态。新的 `tests/resume.test.ts` 覆盖醒来后只自动续一次、同一单不会续两次、被打断的定时委托不重跑。新场景 `sleepwake`：用只在没打包时能用的调试接口模拟睡眠和醒来，替身在醒来时报断网，单子自己接着做完。新场景 `shutdown`：两单在做时模拟关机，下次开店列出两单，都接着做，每个会话在账本里只记一次。`crash`、`stopclose`、`stopdone`、`neterror`、`forgetbusy` 照旧过。
